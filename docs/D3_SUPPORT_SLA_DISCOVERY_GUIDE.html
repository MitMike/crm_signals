Find your Support & SLA setup

A beginner-friendly guide for the person who administers your Frappe / ERPNext site. Follow the steps, collect the answers, and send the report to the CRM Signals team. You do not need to write code or change your site configuration.

Target baseline: Frappe v16.5. Capture the exact patch/build with bench version and the installed ERPNext/Helpdesk versions with bench --site YOUR-SITE-NAME list-apps. The standard HD Ticket / HD Service Level Agreement D3 adapter is already implemented; this guide verifies whether the pilot site's schema matches it.
Pilot calendar expectation: Monday–Saturday business week. Verify the active Helpdesk SLA's actual working days, hours, holiday list and timezone. CRM Signals reads the native SLA policy and does not override it.
First, the important bit: This is a discovery exercise, not a setup exercise. We need to learn which support/ticket system your site already uses and how its SLA clock works. Do not install a new app, rename fields, or change workflows just for this exercise.

What are we trying to find? (ELI5)

Think of a support ticket as a customer asking your team for help.

  • Ticket: the record that says someone needs help.
  • Status: whether the ticket is new, being worked on, waiting, or finished.
  • Resolved time: the actual date and time the team finished the ticket. This is not always the same as “last modified”.
  • SLA: the promise about how quickly the team should respond or solve the problem.
  • SLA clock: the timer. It may pause while waiting for the customer, and it may count only business hours.
  • Business calendar: working days, hours, holidays, and timezone used by that timer.

CRM Signals must read the real ticket and SLA records. It must not guess these rules.

Before you start

You need:

  • A System Manager / site administrator who can open the target Frappe site.
  • Access to the server or Bench command line for the read-only inventory in Step 3. If you do not have this, ask your hosting/implementation partner to run it.
  • A Support or Helpdesk owner who can confirm what “resolved” and “SLA breached” mean for your business.

Time: about 20–40 minutes if the right people are available.

Do not share: passwords, API keys, customer names, ticket descriptions, comments, email addresses, phone numbers, or database exports.

Frappe v16.5.0 compatibility gate: the tested reference uses Helpdesk v1.28.0. Helpdesk v1.29.0 and v1.30.2 desk builds link @framework/ui to apps/frappe/ui, which is absent from the unmodified Frappe v16.5.0 tag. Helpdesk v1.31.1 also requires the Notification Type DocType. The discovery script reports both dependencies for the installed site. For any other Helpdesk release, use the same preflight and verify its actual dependencies; do not install a version whose required dependencies are absent.

Follow these steps in order

  1. Confirm which site you are checking.

    Write down the site/environment name (for example, “staging” or “production”), the date, and who is the technical and business contact. Do not include private hostnames in a report sent outside your company.

  2. Record the installed app versions.

    On the server, run this command from your Bench folder:

    bench version

    Copy the app names and version numbers into the worksheet below. We especially need Frappe, ERPNext, CRM Signals, and any app with a name like Support, Helpdesk, Service Desk, Issue, or SLA.

  3. Run the read-only discovery script.

    Open the site console:

    bench --site YOUR-SITE-NAME console

    Replace YOUR-SITE-NAME with the site's Bench site name. Paste the full script below into the console. It reads installed-app names and DocType/field metadata only. It does not create, update, or delete records.

    Safety: Run this only on the intended site. Review the output before sharing it. The script deliberately does not read ticket rows or customer data.
    import os
import frappe

print("\\n=== INSTALLED APPS ===")
# get_app_path returns apps/frappe/frappe; the linked UI package is at apps/frappe/ui.
frappe_root = os.path.dirname(frappe.get_app_path("frappe"))
print("frappe/ui package present:", os.path.isdir(os.path.join(frappe_root, "ui")))
print("Notification Type DocType present:", bool(frappe.db.exists("DocType", "Notification Type")))
for app in sorted(frappe.get_installed_apps()):
    print(app)

keywords = ("support", "helpdesk", "help desk", "ticket", "issue", "service", "sla")
print("\\n=== POSSIBLE SUPPORT / SLA DOCTYPES ===")
doctypes = frappe.get_all(
    "DocType",
    filters={"istable": 0},
    fields=["name", "module", "custom"],
    limit_page_length=5000,
)
candidates = [
    d for d in doctypes
    if any(k in ((d.name or "") + " " + (d.module or "")).lower()
           for k in keywords)
]
for d in sorted(candidates, key=lambda x: (x.module or "", x.name or "")):
    print("\\n---", d.name, "| module:", d.module, "| custom:", d.custom, "---")
    try:
        meta = frappe.get_meta(d.name)
        for field in meta.fields:
            print(
                field.fieldname,
                "| label:", field.label,
                "| type:", field.fieldtype,
                "| options:", field.options or ""
            )
    except Exception as exc:
        print("Could not read metadata:", type(exc).__name__)

print("\\n=== END: metadata only; no ticket records were read ===")

    Copy the output into your internal worksheet. If the list is very long, share only the likely ticket and SLA DocTypes plus their field lists.

  4. Check the Support / Helpdesk screen in Desk.

    Open the support app your team actually uses. Find one example ticket manually. Note the DocType name (often visible in the URL or from the DocType list), the status choices, and which status values mean “finished”. Do not copy the customer's details.

  5. Find the real resolution timestamp.

    Ask the Support owner: “When a ticket is solved, which field records the actual solved date and time? What happens if it is reopened?” Write the exact field name. Do not assume modified is the resolution time.

  6. Find the SLA rule and clock.

    Ask where the SLA policy is configured and how a ticket is linked to it. Record the SLA DocType, policy field, deadline field, and native result/status that says compliant or breached. Also record whether waiting states pause the clock.

  7. Confirm the business calendar.

    Record working days, start/end of working hours, holiday list, and timezone. Ask whether the SLA uses elapsed hours (24×7) or business hours. If different policies use different calendars, list them separately.

  8. Confirm permissions and retention.

    Ask which roles can read tickets and SLA records (especially Sales User and Sales Manager), and how long old tickets/SLA records are retained. CRM Signals must not show a metric if the logged-in user is not allowed to read its source.

  9. Get business sign-off on the numbers.

    The Support owner and Sales/business owner must agree which tickets count in each KPI: created, resolved, open backlog, resolution time, and SLA compliance. Confirm whether reopened, cancelled, merged, duplicate, or non-SLA tickets are included or excluded.

How CRM Signals will use the answers

  • Tickets created: tickets whose created timestamp is inside the selected date window.
  • Tickets resolved: tickets whose true resolved timestamp is inside that window.
  • Open backlog: tickets currently in a non-terminal status.
  • Average resolution time: created-to-resolved duration. Business hours and elapsed hours will be labelled separately if both are available.
  • SLA compliance: compliant tickets divided by tickets that had a valid, applicable SLA result. Tickets without an SLA are not silently counted as compliant.
  • SLA breaches: tickets marked breached by the installed SLA engine, following its actual rules.
If a source field, SLA result, or permission is missing, the metric should show “Unavailable / not configured”—not a misleading zero.

Common questions

Do I need to install a Support app?

No. First tell us what is already installed. If no support/ticket source exists, record “No support app found”. Do not install one as part of discovery.

What if we use a custom ticket DocType?

That is fine. Record its exact name, owning app, fields, status values, and links. The adapter can be designed around a verified custom source.

Can I just send a screenshot?

Screenshots can help explain a screen, but we need exact DocType and field names. Send the metadata output and completed worksheet as the primary evidence. Hide customer details in any screenshots.

What if I cannot run the console script?

Ask your Frappe hosting provider or implementation partner to run it. They can return the metadata-only output. You can still complete the business questions with your Support owner.

Is this changing anything on the site?

No. The supplied script reads installed app names and DocType metadata. It does not change settings, workflows, tickets, or SLA records.

What happens after I send the answers?

The standard HD Ticket / HD Service Level Agreement adapter is already implemented. We compare the discovered metadata with that contract. If it matches, proceed to configuration and pilot scenarios. If the site uses custom ticket DocTypes or fields, record the exact differences and decide whether a narrowly scoped adapter change is needed. D3 is not pilot-verified until live role permissions, the active SLA calendar and metric results pass.

Where to send the result

Send the completed worksheet and the reviewed metadata-only output to your CRM Signals implementation/technical owner using your company's approved secure channel. Include the environment and date. Do not send credentials or ticket/customer records.

Final rule: If you are unsure, write “Unknown” and ask the Support owner. A correct unknown is safer than a confident guess.

CRM Signals: Support & SLA setup

What is this? This guide helps your Frappe/ERPNext administrator tell CRM Signals which support tickets to count and how to measure service response and resolution.

Target baseline: Frappe v16.5. PR #48 is validating Frappe v16.5.0 + ERPNext v16.5.0 + Helpdesk v1.30.2 (with Telephony). The first v1.31.1 attempt failed during Helpdesk post-install because its Notification Type setup expects a controller absent from exact Frappe v16.5.0; ADR-057 records this compatibility finding. Confirm the exact patch build and installed ERPNext/Helpdesk versions on your pilot site. This guide is read-only until its staging test steps explicitly ask you to create synthetic tickets.

One important rule: the standard Frappe Helpdesk adapter is already implemented for HD Ticket and HD Service Level Agreement. Do not assume the pilot site uses the standard schema: inspect its installed app/version, DocTypes, fields and permissions first. If the metadata matches, proceed with configuration and acceptance. If it differs, record the exact delta and decide whether a narrow adapter change is needed before enabling D3.

Before you start

Step 1 — Find the support app

Think of an app as the toolbox that contains your support desk. In the server terminal, run:

bench --site your-site-name list-apps

Write down every support/helpdesk-related app and its version. Also record the Frappe and ERPNext versions:

bench version

Record: site/environment, Frappe version, ERPNext version, support app name(s), support app version(s).

Step 1A — Confirm the v16.5 target

The expected framework baseline is Frappe v16.5. Do not record only “v16”: capture the exact patch build from bench version, plus the installed ERPNext and Helpdesk versions. The CI v15/v16 matrix is compatibility evidence, not proof of this site's patch level or configuration.

Stop if versions are unexpected. Do not install a new support app to make the dashboard appear. Record the mismatch and validate the installed version/source before enabling D3.

Step 2 — Find the ticket record type

A DocType is like a spreadsheet template: it defines what a ticket record looks like. We need its exact name, not a guess.

Open the Frappe bench console:

bench --site your-site-name console

Paste this read-only discovery snippet. It lists likely support DocTypes and their field definitions, not ticket contents.

import frappe

print("Installed apps:")
for app in frappe.get_installed_apps():
    try:
        print(app, frappe.get_attr(app + ".__version__") if frappe.get_attr(app + ".__version__") else "")
    except Exception:
        print(app)

keywords = ("support", "ticket", "issue", "helpdesk", "service", "sla")
rows = frappe.get_all(
    "DocType",
    fields=["name", "module", "custom"],
    limit_page_length=0
)
for row in rows:
    text = (row.name + " " + (row.module or "")).lower()
    if any(word in text for word in keywords):
        print("\\nDOCTYPE:", row.name, "| module:", row.module, "| custom:", row.custom)
        try:
            meta = frappe.get_meta(row.name)
            for field in meta.fields:
                print("  ", field.fieldname, "|", field.label, "|",
                      field.fieldtype, "| options:", field.options)
        except Exception as exc:
            print("  Could not read metadata:", str(exc))

If the app-version expression errors on your Frappe version, skip that version line and use bench version from Step 1. The DocType and field metadata portion is read-only.

Good: this inspects configuration and schema. It does not fetch ticket rows, customer names, email addresses, comments, or attachments.

Step 2A — Check the standard Helpdesk fields and permissions

The initial adapter reads aggregate values from HD Ticket and checks the HD Service Level Agreement DocType. It does not read ticket subjects, comments, contacts or ticket identifiers. Confirm the following fields exist in the installed version:

Run this read-only check in bench --site your-site-name console. Replace the two example user IDs with the actual Sales User and Sales Manager accounts. It reports permission names only; it does not read ticket rows.

import frappe
from frappe.model import get_permitted_fields

required = (
    "status_category",
    "resolution_date",
    "resolution_time",
    "sla",
    "agreement_status",
)
for user in ("sales.user@example.com", "sales.manager@example.com"):
    allowed = set(get_permitted_fields(
        "HD Ticket", user=user, permission_type="read"
    ))
    print(user, {
        "ticket_read": frappe.has_permission("HD Ticket", ptype="read", user=user),
        "sla_read": frappe.has_permission(
            "HD Service Level Agreement", ptype="read", user=user
        ),
        "fields": {field: field in allowed for field in required},
    })
Do not grant elevated Helpdesk field access automatically. Field permlevels vary by Helpdesk release: the v1.30.2 reference fields are all permlevel 0, while later releases may define elevated levels. Have the Helpdesk/security owner inspect the full field set and approve the narrowest safe policy. CRM Signals marks an affected metric unavailable rather than misreporting zero when a field is not readable.

Reference role map for Helpdesk v1.30.2 on Frappe v16.5.0: the D3 fields status_category, resolution_date, resolution_time, sla and agreement_status are all at permlevel 0. HD Ticket read is granted to System Manager, Agent, Agent Manager, HD Customer and HD Customer Manager. The HD Service Level Agreement DocType grants read to System Manager and Agent Manager. ERPNext Sales User and Sales Manager are not default Helpdesk readers. For any other installed Helpdesk release, inspect its actual field permlevels and DocType read roles before applying a permission map.

Do not assign Agent or Agent Manager to Sales users just to show this dashboard; those roles also grant ticket create/write privileges; Agent Manager additionally has delete permission. If Sales needs D3, create a dedicated read-only role with only the required HD Ticket field access at the installed version's actual permlevels; grant HD Service Level Agreement read only if SLA metrics are required. Add this role to the approved Sales users/managers. Re-run the metadata preflight after every Helpdesk upgrade.

Ticket DocType read permission is required for ticket metrics. SLA DocType read permission plus the required ticket fields is required for SLA metrics. Missing SLA access does not have to disable ticket creation/backlog metrics.

Step 3 — Tell us how a ticket works

For the ticket DocType you found, identify these fields from the metadata and the support team's normal process:

  • Ticket ID: the unique record name.
  • Customer link: field linking the ticket to a Customer or Lead, if present.
  • Status: field and all its possible values (Open, Working, Resolved, Closed, Reopened, etc.).
  • Resolved at: the field that records the actual resolution date/time.
  • Reopened: what happens to the resolution timestamp and status when a customer replies?

Do not use “Last Modified” as the resolution date unless the support process explicitly proves it means resolution.

Step 4 — Find the SLA rules

SLA means the service promise, for example “respond within 2 working hours” or “resolve within 2 business days.” We need the system's real rule and result.

  • What DocType stores SLA policies?
  • How is a policy linked to a ticket?
  • Which fields hold the deadline and actual SLA outcome (met/breached)?
  • Can the clock pause while waiting for the customer?
  • What happens when a ticket is reopened?

Do not calculate compliance from ticket status alone if the installed SLA engine already records the authoritative result.

Step 5 — Confirm the business clock

Business hours are not always 24/7. Confirm:

  • Site timezone (Frappe System Settings).
  • Working days and daily start/end times.
  • Holiday list and regional holidays.
  • Pause/resume rules and which statuses pause the clock.
  • Whether leadership wants elapsed time, business time, or both (shown separately).

Step 6 — Confirm access and retention

  • Can Sales User read ticket metadata?
  • Can Sales Manager read ticket and SLA metadata?
  • Are permissions different for different teams or Companies?
  • How long are tickets and SLA records retained?
  • Are deleted/archived tickets still available for reporting?

CRM Signals should show aggregate counts and durations, not ticket descriptions, comments, or personal details.

What happens after you return this?

  1. Compare the installed Helpdesk metadata with the existing standard adapter contract.
  2. Confirm the KPI definitions and least-privilege field access for the intended Sales roles.
  3. If the standard schema matches, no new adapter is required; configure the app and run the staging scenarios. If the site is customized, record the exact differences and decide on a narrowly scoped change.
  4. Test status changes, reopened tickets, SLA pauses, holidays, timezone and access restrictions.
  5. Only after live role permissions, the active SLA calendar and metric results pass should D3 be treated as pilot-verified.

Do not install a new support app just for this task. First discover what the site already uses. If no support/SLA system exists, we will record that as a business decision rather than silently inventing one.
